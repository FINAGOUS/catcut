## 1. 解码（导入 → 探测 → 解码）

“解码路径”列：`D3D11VA→软解` = 优先硬件，失败自动回退软解并记录
实际走的路径；`软解` = 只有软件解码器。最高分辨率栏是 FFmpeg
解码器本身的上限（受显存/内存限制），不是 CatCut 的承诺——8K
已用探针素材在云端软解验证通过（见 verify-s1），更高分辨率未验证。

### 2.1 代理编码器（S1 已实现，运行时探测，顺序固定）

| 顺序 | 编码器 | 编码 | 用途 | 状态 |
|---|---|---|---|---|
| 1 | libopenh264 | H.264 | 720p/540p 代理 | BtbN LGPL 包内含（静态链进 avcodec.dll）；verify-s1 打印实际选中项 |
| 2 | libvpx-vp9 | VP9 | 720p/540p 代理 | 备选；verify-s1 打印实际选中项 |
| 3 | mpeg4 | MPEG-4 Part 2 | 720p/540p 代理 | 兜底；始终可用 |
| — | libx264 / libx265 | — | — | **GPL，永不使用**；构建时 CMake 与工作流双重检查 |

代理参数：MP4 容器，YUV420P，4 Mbps，GOP = 帧率，B 帧 0；720p
优先，源片低于 720p 时不放大。代理只用于预览，导出永远从原始
素材重链；代理缺失是硬错，不静默回退原片。

## 3. 导入失败原因对照（导入失败时 UI 按此给可读原因）

| 现象 | 原因 | 给用户的说法 | 出路 |
|---|---|---|---|
| 文件不存在 | 路径错 / 文件被移动 | “文件不存在：<路径>” | 重新定位 |
| 打不开 / 无流 | 文件头损坏、截断、空文件 | “打不开文件（容器无法识别或文件头已损坏）” | 重新拷贝/修复源文件 |
| 无音视频流 | 裸流、未支持的容器 | “文件中没有可识别的音视频流” | 转码后导入 |
| 缺解码器 | 编码无对应解码器 | “缺少解码器：编码 <名> 没有可用的解码器” | 转码后导入 |
| profile 不支持 | 如 HEVC 10-bit 4:2:2、12-bit | 探测信息 + “该 profile 暂不支持硬件解码，已用软解；如仍打不开请转码” | 一键转代理/转码（S2 接入） |
| 显存不足 | 8K 硬解显存不够 | 解码失败时报具体 FFmpeg 错误 | 回退软解 / 生成代理后剪辑 |
| 帧率/时长未知 | 元数据缺失 | 探测 warning，不阻断导入 | 按默认值处理 |

## 4. 为什么 8K 会打不开（对照三家调研 §5.2）

按可能性排序，CatCut v2 的对策写在每条后面：

1. **编码 profile 不支持**：8K 素材几乎总是 HEVC 10-bit 4:2:2；
   Windows 默认缺 HEVC 解码器（需另购 HEVC Video Extensions），
   很多解码器不实现 10-bit 4:2:2。对策：本矩阵公开支持情况；
   导入失败说清是哪个 profile；给一键转代理出路。
2. **硬件解码能力不足**：8K 解码算力是 4K 的 4 倍。对策：
   D3D11VA 失败自动回退软解并告知；代理默认开。
3. **代理未开 + 预览策略**：未开代理时 8K 原片直接上时间线，
   实时解码跟不上，表现为打不开/卡死。对策：代理默认开，
   预览按监视器尺寸解码。
4. **文件本身问题**：云盘占位符、文件损坏、MKV 改名、裸流。
   对策：探测阶段即报可读原因，不等到播放才崩。

## 5. 未验证清单（不要当事实引用）

- HEVC 12-bit、VP9 10/12-bit 8K、AV1 8K 的实测解码速度与丢帧率。
- D3D11VA 对 H.264/HEVC 4:2:2、4:4:4 的接管情况（因 GPU 而异）。
- WMV/FLV、DTS 音频的实测导入。
- ProRes / AV1 导出编码。
- Mac（VideoToolbox）侧全部内容——Mac 版立项时重写。
- 任何硬件编解码的真机数据——云端无 GPU，待用户电脑实测。
